# Retrieval: embeddings, hybrid search and its evaluation

Everything here is measured on the 25,000-product catalogue described in
[catalogue.md](catalogue.md). The numbers come from
`.captures/reports/retrieval-evaluation.json` and `.captures/reports/vector-latency.json`,
regenerated by `yarn eval:run` and `yarn bench:vector`.

The question this phase answers is narrow and worth stating plainly: **does
semantic retrieval actually beat PostgreSQL full-text search on this corpus, and
by how much?** It was possible for the answer to be "no".

## The evaluation set came first

72 queries in 9 categories were written and labelled **before any embedding
existed**, so no label could be chosen to flatter a vector result. The labels
were produced by `yarn eval:label`, which ranks candidates lexically and by
metadata, and were then reviewed by hand. `evaluation/qrels.json` records the
fingerprint of the query set it was built for, and `eval:run` reports it; if the
queries change, the mismatch is visible.

| category | n | what it probes |
|---|---|---|
| `exact_product` | 10 | a named product ("heinz baked beans") |
| `brand` | 8 | brand recall ("cathedral city") |
| `synonym_uk` | 11 | UK vocabulary ("courgette", "aubergine", "swede") |
| `semantic_intent` | 10 | intent, not words ("something to spread on toast") |
| `similarity` | 7 | "like X, but …" |
| `dietary` | 7 | claim-driven ("vegan cheese") |
| `nutrition` | 7 | with structured bounds ("high protein snack") |
| `category_ambiguity` | 7 | one word, many senses ("milk", "chips", "cream") |
| `known_failure` | 5 | the five failures documented for the FTS baseline |

Grading is deliberately strict. Grade 2 means "this is what the query asked
for"; grade 1 means "related and acceptable". **Recall, precision and MRR count
grade 2 only** — a strategy cannot score well by returning near-misses. Grade 1
earns partial credit in nDCG@10 alone.

Recall@k is capped: `|relevant ∩ top k| / min(k, |relevant|)`. Some queries have
hundreds of relevant products ("crisps": 822), where uncapped recall@10 could
never exceed 0.012 and would measure corpus size rather than ranking.

## Embeddings are derived data, not part of the model

`product_embedding` is a separate table keyed by `(barcode, model)`, recording
`dimensions`, `document_version`, `text_hash`, `embedded_at` and the run that
produced it. Nothing in the `Product` contract knows embeddings exist, and the
whole table can be dropped and rebuilt from the catalogue.

The `text_hash` is the hash of the semantic document, the same value change
detection stores on `product`. Two consequences follow, both enforced in SQL:

- **Re-embedding is driven by meaning, not by rows.** A product whose price or
  image changed is not re-embedded; a product whose name, brand, category,
  ingredients or quantity changed is. On the run below, 24,936 of 25,000
  products were embedded and 64 skipped as already fresh.
- **A stale vector can never be searched.** Vector queries join
  `e.text_hash = p.text_hash AND e.document_version = p.document_version`. An
  embedding of an older document is invisible until it is rebuilt, rather than
  quietly returning a product that no longer says what the vector says.

`embedProducts` rebuilds each document and compares its hash to the stored one
before embedding it. A mismatch is reported as `text_hash_mismatch` rather than
embedded, because it means the catalogue itself is inconsistent.

## Choice of model: local, not hosted

| | BGE-small-en-v1.5 (chosen) | OpenAI `text-embedding-3-small` |
|---|---|---|
| dimensions | 384 | 1536 |
| licence / cost | MIT, free | $0.02 / 1M tokens ≈ **$0.10** for this corpus |
| key required | no | yes |
| query latency | 2.6 ms local | a network round trip |
| reproducible | yes, pinned revision | version is the provider's to change |

Cost was not the deciding factor — ten cents is nothing. The deciding factors
were that a portfolio project anyone can clone should not need an API key, and
that a pinned model revision (`ea104dac…`, fp32, CLS pooling) makes the numbers
in this document reproducible. The `Embedder` interface is provider-neutral, so
a hosted model is a drop-in swap; the model id is stored on every row, so two
models can coexist during a migration.

The test suite uses `HashingEmbedder`, a deterministic hashing embedder with no
semantic knowledge at all. It keeps the suite **network-free and free of paid
APIs** while still exercising storage, staleness, filtering and fusion. It
cannot be used to judge relevance, and the tests do not ask it to.

| failed | **0** |

| throughput | ~8 products/s (CPU, fp32, batch 64) |

The run is restartable and idempotent, and this was tested the hard way rather
than in theory: Docker Desktop died mid-run when the machine ran out of disk.
The 64 embeddings written before the crash were intact, and the restarted run
skipped exactly those 64. A second run immediately after completion embeds
nothing and rewrites no rows.

## Exact search, and why there is no ANN index

25,000 vectors × 384 dimensions is about 37 MB — small. Measured over 216
searches (72 queries × 3 repeats), limit 10:

| | mean | p50 | p95 | max |
|---|---|---|---|---|
| encode the query | 2.6 ms | 2.6 ms | 2.9 ms | 3.4 ms |
| exact cosine scan | 23.2 ms | 22.9 ms | 23.9 ms | 60.2 ms |
| exact scan + structured filters | 15.0 ms | 14.9 ms | 15.8 ms | 19.7 ms |
| **end to end** | **25.8 ms** | **25.4 ms** | **26.7 ms** | 63.2 ms |

An HNSW or IVFFlat index would trade exact results for speed this corpus does
not need — and would add build time, memory, and a recall parameter to tune. It
is the right change at perhaps 10× this corpus, not at 25,000 rows. Filters make
the scan *faster*, because they remove rows before the distance sort.

## The four strategies

```
fts                PostgreSQL FTS: weighted tsvector, websearch_to_tsquery, ts_rank_cd
fts_normalised     the same, with deterministic UK/US term expansion
vector             exact pgvector cosine over product embeddings
hybrid             RRF over fts + vector          (hybrid_normalised: fts_normalised + vector)
```

**Terminology normalisation** (`src/retrieval/terminology.ts`) expands a query
into an AND of ORs: "tinned tuna" becomes `tinned|canned` AND `tuna`. It holds
20 entries covering three narrow, defensible classes — British/American
spellings (yoghurt/yogurt), British/OFF vocabulary (tinned/canned,
aubergine/eggplant), and compounds written both ways (cornflakes/corn flakes).
It is deliberately *not* a hand-maintained synonym dictionary aimed at the
evaluation set: it touches only 11 of the 72 queries, and the table below reports
the other 61 separately so its effect cannot be mistaken for the model's.

**Fusion** is Reciprocal Rank Fusion, `score = Σ weight / (k + rank)` with
k = 60, over the top 50 from each strategy. It uses ranks, not scores, so
`ts_rank_cd` and cosine distance never have to be made commensurable — and it
needs no LLM and no reranker.

**Structured requirements are not retrieval.** Nutrition bounds, dietary
policies, allergen exclusions, categories and quality tiers are SQL predicates
applied inside every strategy, so ranking cannot overrule them. Two policies are
deliberately conservative:

- A missing nutrient value never satisfies a bound, in either direction.
- Allergen exclusion requires positive evidence: a product whose allergen status
  is `unknown`, or whose declaration contains an allergen this system does not
  recognise, is excluded rather than assumed safe. Every hit carries
  `allergenEvidence` (`listed` / `none_listed` / `unknown`) so a caller can say
  "none listed" rather than "free from".

## Results

72 queries, limit 10, fusion depth 50, k = 60.

| strategy | recall@5 | recall@10 | prec@5 | MRR | **nDCG@10** | zero results | p50 | p95 |
|---|---|---|---|---|---|---|---|---|
| fts | 0.575 | 0.564 | 0.575 | 0.649 | 0.582 | 20.8% | 0.6 ms | 10.8 ms |
| fts_normalised | 0.647 | 0.637 | 0.647 | 0.699 | 0.654 | 19.4% | 0.5 ms | 4.3 ms |
| vector | 0.750 | 0.752 | 0.750 | 0.812 | 0.776 | 0.0% | 27.9 ms | 30.8 ms |
| hybrid | 0.778 | 0.773 | 0.778 | 0.833 | 0.796 | 0.0% | 28.2 ms | 30.0 ms |
| **hybrid_normalised** | **0.792** | **0.798** | **0.792** | **0.847** | **0.819** | **0.0%** | 28.1 ms | 29.4 ms |

Hybrid retrieval is better than lexical search on this corpus by 0.237 nDCG@10,
and the gain is not an artefact of the terminology list: on the 61 queries the
list cannot touch, FTS scores 0.610 and hybrid 0.808.

The single most useful number is the **zero-result rate**. Lexical search
returns nothing at all for 1 query in 5 — 86% of similarity queries and 60% of
intent queries — and a grocery assistant that answers "no results" to "something
to spread on toast" is useless regardless of how well it ranks "heinz beans".

| category | fts | fts_norm | vector | hybrid | hybrid_norm |
|---|---|---|---|---|---|
| exact_product | 0.936 | 0.936 | 0.905 | 0.953 | 0.953 |
| brand | 0.966 | 0.966 | 0.879 | 0.992 | 0.992 |
| synonym_uk | 0.709 | 0.940 | 0.751 | 0.819 | 0.921 |
| semantic_intent | 0.087 | 0.087 | 0.451 | 0.438 | 0.438 |
| similarity | 0.031 | 0.031 | 0.767 | 0.767 | 0.767 |
| dietary | 0.663 | 0.663 | 0.877 | 0.841 | 0.841 |
| nutrition | 0.426 | 0.597 | 0.895 | 0.833 | 0.847 |
| category_ambiguity | 0.736 | 0.736 | 0.693 | 0.715 | 0.715 |
| known_failure | 0.631 | 0.914 | 0.873 | 0.871 | 0.966 |

Read across the rows rather than down the columns, because the strategies are
good at different things:

- **Lexical search is better at names.** For brands and exact products it is
  already at 0.94–0.97, and vector search is *worse* (0.879, 0.905). Embeddings
  blur precisely the distinctions — Cathedral City vs any other mature cheddar —
  that a brand query is asking about.
- **Vector search is better at intent and similarity**, where FTS scores 0.087
  and 0.031 because the words in the query do not appear in the corpus.
- **Normalisation beats vector search at its own game.** On the UK-vocabulary
  queries it reaches 0.940, above vector's 0.751, for 20 table entries and no
  model. Cheap deterministic normalisation is worth doing *before* reaching for
  a model, not after.
- **Vector search leads on dietary and nutrition** — but those queries also carry
  structured filters, so this compares ranking *within* an already-correct
  candidate set, not the correctness of the filtering.
- **Ambiguity is the one category nothing solves** (0.69–0.74 across the board).

Hybrid is better than plain FTS on 39 of 72 queries, worse on 9, unchanged on 24;
and better than vector alone on 23 of 36 queries where they differ. Fusion is
not free, and the regressions are documented below rather than averaged away.

## The five known FTS failures

These were documented as baseline failures before this phase began.

| query | fts | cause | fixed by |
|---|---|---|---|
| "tinned tuna" | **0.000, zero results** | the corpus says "canned"; the tokens never meet | normalisation → 1.000 |
| "cornflakes" | 0.584 | stems to `cornflak`, which matches "Cornflake Cluster Bites" (chocolate) before the cereal | normalisation → 1.000 |
| "oat milk" | 0.571 | "Oat milk chocolate Orange" outranks actual oat drinks; both contain both words | vector 0.782, hybrid 0.832 — partial |
| "greek yoghurt" | 1.000 | — the predicted spelling failure did not occur: the corpus contains both spellings, and enough products say "yoghurt" | — |
| "salted butter" | 1.000 | — no failure either: the phrase appears verbatim in product names | — |

Three of the five were real and all three are fixed or improved. **Two were not
failures at all** once measured against the full corpus — which is the argument
for building the labelled set before the fix rather than after it. "oat milk"
remains imperfect for everybody: no strategy distinguishes "milk made of oats"
from "milk chocolate with oats", because that is a compositional question about
what modifies what.

## The ten worst queries, and why

Under the best strategy (`hybrid_normalised`), worst first.

1. **"cheese for a toastie"** (0.000) — every hit is a *toastie product*: Starbucks Five Cheese Toastie, Herta ham-and-cheese toasties, Warburtons Toastie bread. The query asks for an ingredient for a purpose; both strategies match the artefact named in the query. Nothing in the corpus states which cheeses melt.
2. **"something to spread on toast"** (0.064) — retrieves toast, not spreads. The intent word ("spread") is swamped by the object word ("toast"), and the embedding of a jam jar contains no mention of toast. 783 products are relevant; the ranking finds one at rank 10.
3. **"milk alternative for coffee"** (0.106) — returns coffee: Lavazza Cappuccino, Costa Latte, a coffee whitener. The literal term "coffee" dominates the compositional request "a milk alternative, for use in coffee".
4. **"sauce for spaghetti bolognese"** (0.148) — returns ready meals *called* spaghetti bolognese rather than jars of sauce. Same failure as (1): the dish name outranks the component.
5. **"breakfast cereal for children"** (0.212) — returns cereals, but not children's cereals: nothing in the product data marks a product as aimed at children, so the qualifier cannot be honoured by any retrieval method.
6. **"vegan chocolate"** (0.249) — retrieves vegan chocolate *cake*, *ice cream*, and oat-milk chocolate bars. The grade-2 set was restricted to chocolate confectionery; the strategy cannot tell that "chocolate" here means the bar and not the flavour.
7. **"chips"** (0.333) — returns tortilla chips (grade 1) ahead of British chips/fries (grade 2). A genuine ambiguity: the corpus's American-English labelling is at odds with a UK user's meaning, and no ranking can resolve it without knowing the locale.
8. **"hot drink before bed"** (0.356) — ranks hot chocolate first, correctly, then fills with energy drinks. "Drink" matches; "before bed" — which should *exclude* caffeine — is not represented anywhere in the data.
9. **"milk"** (0.425, against FTS's 1.000) — **the clearest hybrid regression.** FTS ranks products literally named "Milk" first. Vector search pulls in Dairy Milk chocolate, infant formula and flavoured milk, and fusion lets them displace plain milk. Semantic similarity is exactly the wrong tool for a one-word head term.
10. **"cream"** (0.471, against FTS's 0.066) — the same ambiguity resolved the other way: FTS drowns in "ice cream" and "cream crackers", hybrid recovers real dairy cream at ranks 2, 3 and 5.

Three causes, in order of how much they matter:

- **Compositional intent** (1, 2, 3, 4, 6): "X for Y" and "X made of Y" are relations, and neither bag-of-words nor a single embedding represents relations. This is the failure class that a query-understanding step — an LLM decomposing the request into a product type plus constraints — would address. That is the next phase, and it is the honest justification for one.
- **Information the corpus does not contain** (5, 8): no amount of retrieval will find a "for children" or "caffeine-free at night" signal that was never recorded. The fix is data, or an explicit admission of ignorance.
- **Head-term ambiguity** (7, 9, 10): short queries where the strategies disagree — and where hybrid is not uniformly better. This is a real cost of fusion, not a rounding error.

Eight of the nine are one- or two-word queries naming a product type exactly —
the case where lexical matching is already right and semantic neighbours can
only dilute it. A defensible improvement is to weight the lexical list higher
when the query is short and matches many products exactly, which `fusion.lexicalWeight`
already supports. **It has not been tuned**, because tuning fusion weights
against the same 72 queries used to report the result is how an evaluation set
gets burned; that needs a held-out set.

## Reproducing it

```bash
yarn db:migrate        # includes 002_embeddings.sql (pgvector)
yarn embed             # ~52 min on CPU, restartable, idempotent
yarn bench:vector      # exact-search latency
yarn eval:run          # the table above → .captures/reports/retrieval-evaluation.json
```

`yarn test` covers all of it against PGlite with the hashing embedder: no
network, no API key, no PostgreSQL server, no model download.

## Limitations

- **72 queries is small.** Differences of a few points are not significant; the
  gaps reported above (0.582 → 0.819, 20.8% → 0% zero results) are large enough
  to act on, and the per-category rows are 5–11 queries each and should be read
  as direction, not measurement.
- **The labels are mine.** They were frozen before any vector result existed and
  the two revisions made afterwards are recorded, but a single labeller has
  blind spots — particularly on grade 1 vs grade 2 in ambiguous categories.
- **English only**, single locale, and the corpus's own labelling is partly
  American ("chips", "canned"), which the terminology list only partly bridges.
- **Fusion weights are untuned** and, deliberately, were not tuned here.
- Nothing in this phase generates text. There is no LLM, no reranker, no
  generation, and no claim about answer quality — only about retrieval.
